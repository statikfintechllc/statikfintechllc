# 🌐 Global Components

Shared UI primitives consumed across every StatikFinTech LLC surface. The global layer now ships distinct **desktop** and **mobile** variants so the build tooling can assemble domain bundles with the right footprint automatically.

## 📁 Directory Structure

```text
global.c/
├── README.md
├── desktop/
│   ├── README.md
│   ├── card.js
│   ├── footer.js
│   ├── navbar.js
│   ├── navbar-example.html
│   ├── svg-card.js
│   └── ticker.js
└── mobile/
    ├── README.md
    ├── card.js
    ├── footer.js
    ├── navbar.js
    ├── navbar-example.html
    ├── svg-card.js
    └── ticker.js
```

Each mobile module extends its desktop counterpart (loaded first) and adjusts layout, spacing, or behaviour for smaller screens.

## 🧩 Component Highlights

- **Navbar** – Fixed-height navigation shell with responsive menus.
- **Footer** – Multi-section footer with social, legal, and contact rollups.
- **Card / SVG Card** – Storytelling tiles for copy-heavy or SVG-forward content.
- **Ticker** – Mobile-first ticker slot (desktop ships a hidden placeholder for consistency).

## 🎨 Theming

Global components resolve their styling through the shared `SFTiThemes` registry. Domain-specific colours are generated by the build pipeline from the styles that live under `src/<domain>/<domain>.styles/`. Components simply read from the registry and therefore adapt automatically when new tokens are introduced.

## 🔧 Usage

```html
<script src="/src/components/global.c/desktop/navbar.js"></script>
<script src="/src/components/global.c/mobile/navbar.js"></script>
<script>
  createSFTiNavbar(SFTiNavbarConfigs.main);       // desktop default
  createMobileSFTiNavbar(SFTiNavbarConfigs.dev);  // mobile override
</script>
```

When embedding mobile overrides ensure the desktop variant script loads first so the prototype chain is available.

## 🔄 Maintenance

1. Update the desktop implementation first.
2. Mirror API changes in the mobile wrapper (even if it simply forwards calls).
3. Add regression tests or usage notes in the per-variant README.md files.
4. Re-run `src/build/build.sh` with the relevant target domain(s) to verify outputs.

Keeping parity between variants ensures the automated build flow can project components into any domain without manual tweaks.
